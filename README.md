# My Ideal Pennant Race — PHASE 3.2

プレイヤーが**プロ野球球団の監督兼GM**となり、選手を直接操作せず、**選手編成と采配**でチームを勝利へ導く球団経営シミュレーション。

このリポジトリは **PHASE 1（実際に遊べる最小完成版）** に、
**PHASE 2（選手の個性と成長）**、**PHASE 2.5（調子の実効能力への反映）**、
**PHASE 3.1（引退・ドラフト・世代交代）**、**PHASE 3.2（スカウト）** を追加したものです。

> **PHASE 1 の目的**は「見た目が完成すること」ではなく、
> 球団を選ぶ → 選手を見る → 1軍を編成する → 打順を決める → 試合をする → 勝敗が決まる →
> 成績が変わる → 順位が変わる → 日付が進む → セーブされる
> という一連のゲームループが**完全に動作すること**です。

## スマートフォンで遊ぶ

### A. 1枚のHTMLファイルにして持ち歩く（いちばん手軽）

```bash
npm run build:single      # dist/my-ideal-pennant-race.html が出来る
```

出力された HTML は JS も CSS も内蔵した**完全に自己完結した1ファイル**です。
AirDrop・クラウドストレージ・メール添付などでスマートフォンに送り、ブラウザで開けばそのまま遊べます。
Safari の「共有 → ホーム画面に追加」/ Chrome の「ホーム画面に追加」をしておくと、
アドレスバーのないフルスクリーンでアプリのように起動できます。

### B. 同じ Wi-Fi のPCから開発サーバーを開く

```bash
npm run dev -- --host     # 表示された Network: http://192.168.x.x:5173/ をスマホで開く
```

PC とスマートフォンを同じ Wi-Fi につないでおく必要があります。コードを直すとその場で反映されます。

### C. 静的ホスティングに置く

`npm run build` の出力（`dist/`）はどこに置いても動く静的ファイルです（相対パス出力）。
GitHub Pages / Netlify / Vercel などにそのまま配置できます。

> **セーブデータについて**
> セーブは開いたブラウザの localStorage に保存されます。
> PCとスマートフォン、あるいは別のブラウザの間でセーブデータは共有されません。
> シークレットモードやサイトデータの削除でも消えるのでご注意ください。

## PHASE 2：選手の個性と成長

18歳のGランク選手が2軍で育ち、1軍に上がり、主力になり、30代で衰えていく——
そんな選手一人ひとりの物語が自然に生まれるようにするのが PHASE 2 の目的です。

| 要素 | 内容 | 実装 |
| --- | --- | --- |
| 年齢 | シーズン終了時に1歳加算。18〜38歳 | `domain/season.ts` |
| 潜在能力 | 1〜100。**数値は表示せず**「将来性：非常に高い〜非常に低い」で表示 | `domain/growth.ts` |

| 成長 | 年齢・成長タイプ・性格・潜在能力・出場経験・成績・モチベーションの積で決まる | `domain/growth.ts` |
| 衰退 | 31歳以降。走力・球速は早く、制球・守備・捕球は緩やかに落ちる | `domain/growth.ts` |
| 性格 | 努力家・天才肌・負けず嫌い・冷静・リーダー・ムードメーカー・繊細・マイペース・野心家・職人気質 の10種 | `domain/personality.ts` |

| モチベーション | 出場機会・活躍・勝敗で変動。成長量と実効能力に影響 | `domain/condition.ts` |
| 怪我 | 軽傷（数日）/ 中傷（数週間）/ 重傷（数ヶ月）。疲労が高いほど発生しやすい | `domain/injury.ts` |
| スランプ | 不振が続くと一時的に実効能力が低下。時間経過・好調で回復 | `domain/condition.ts` |
| 覚醒 | 若手・高潜在・高モチベーション・一定以上の出場で低確率発生 | `domain/growth.ts` |

### 基本能力と実効能力を分ける

パワー70の選手の**基本能力は70のまま**です。疲労や不調の影響は毎試合
「実効能力」として計算され、選手本来の力と当日の調子を区別しています。

```
実効能力 = 基本能力 × clamp(1 + 疲労 + モチベーション + スランプ + チーム士気 + 性格
                              + 調子（能力カテゴリ別）, 0.72, 1.16)
```

掛け算が積み重なって極端にならないよう、最終倍率は **0.72〜1.16 倍**に制限しています
（`domain/effective.ts`）。特殊能力は能力値ではなく**イベント発生率への係数**として働き、
効果キーごとに上限を設けています（`domain/specialAbilities.ts`）。

## PHASE 2.5：調子（コンディション）

「調子が良い＝全能力◯倍」にはせず、**能力カテゴリごとに効き方を変えて**います。

| 調子 | ミート系 | パワー系 | 走力系 | 守備系 | 球威系 | 制球系 | 変化球系 | スタミナ系 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 絶好調 | +6% | +5% | +4% | +4% | +5% | +4% | +4% | +3% |
| 好調 | +3% | +2% | +2% | +2% | +3% | +2% | +2% | +1% |
| 普通 | ±0% | ±0% | ±0% | ±0% | ±0% | ±0% | ±0% | ±0% |
| 不調 | -3% | -2% | -2% | -2% | -3% | -2% | -2% | -1% |
| 絶不調 | -6% | -5% | -4% | -4% | -5% | -4% | -4% | -3% |

弾道は打球の性質なので調子では変わりません。

### 調子の変化（隣接遷移）

調子は毎日更新されますが、**1段階ずつしか動きにくい**マルコフ連鎖になっています
（絶不調からいきなり絶好調へは飛びません。2段階以上の移動は全変化の15%未満）。
移りやすさは「その段階の出やすさ × 現在からの距離 × 疲労・モチベーション・士気によるバイアス」で決まり、
乱数は呼び出し側から渡すのでシードを固定すれば再現できます。

疲労が高いと好調になりにくくなりますが、**疲労が高い＝必ず不調ではありません**。

### 性格との相互作用

| 性格 | 調子まわりの効果 |
| --- | --- |
| 努力家 | 不調の低下を **-20%**、絶不調の低下を **-15%** 軽減 |
| 繊細 | 調子の振れ幅が **1.45倍**（好調の上振れも不調の下振れも大きい） |
| 冷静 | 調子の振れ幅が **0.85倍** |
| 職人気質 | 調子の振れ幅が **0.85倍**（波が小さい） |
| マイペース | 調子の振れ幅が **0.6倍**、疲労の影響も **0.6倍** |
| ムードメーカー | チーム士気の影響を **1.5倍**受ける |

### 特殊能力との相互作用

特殊能力は能力値に加算せず、既存どおりイベント発生率への係数として働きます。
調子はその係数の「1からのズレ」を拡大・縮小します（絶好調 ×1.12 / 絶不調 ×0.88）。
好調なら長所が出やすく短所が出にくく、不調ならその逆になります。
効果キーごとの上限は変わらず最後に適用されます。

### 調子の検証結果（143試合 × 10シーズン = 8,580試合）

| 調子 | 出現率 | 打率 | 本塁打率 | 防御率 | 奪三振率 |
| --- | --- | --- | --- | --- | --- |
| 絶好調 | 7.3% | .273 | 2.44% | 3.74 | 7.70 |
| 好調 | 16.5% | .268 | 2.32% | 3.89 | 7.56 |
| 普通 | 33.3% | .262 | 2.30% | 4.04 | 7.30 |
| 不調 | 25.6% | .254 | 2.24% | 4.30 | 6.97 |
| 絶不調 | 17.2% | .252 | 2.11% | 4.60 | 6.83 |

* **打線の調子が良い側の勝率は .515** — 調子だけで勝敗が決まることはありません。
* 実効能力倍率の実測値は **0.753〜1.109**（平均 0.991）で、制限の 0.72〜1.16 の内側に収まります。
* 1シーズン目の出現率は 絶好調8.3% / 好調18.9% / 普通32.6% / 不調24.9% / 絶不調15.4% と目標分布どおりです。

### 怪我と7日ルール

怪我をした選手は自動的に1軍から外れ、オーダー・ローテーションからも除外されます。
**怪我による抹消は7日間の登録変更制限の例外**で、復帰後はすぐ再登録できます。
怪我人が増えて1軍の野手が9人・投手が5人を割りそうなときは、2軍から自動で繰り上げます。

### バランス確認（10シーズン自動シミュレーション）

`npx vite-node scripts/balance.ts 10` の結果（143試合 × 10年）：

* 全選手の平均総合 **37.5 → 38.5**（能力インフレなし）
* 総合ランクは G〜A に分散（全員が同じ能力にはならない）
* 22歳以下は平均 **+2.4**、33歳以上は平均 **-0.6**（若手は伸び、ベテランは衰える）
* 怪我は **1球団あたり年 4〜6件**、1試合あたりの発生率は 5% 未満
* 1軍選手の平均疲労 **17〜22**、コンディションは 絶好調8% / 好調19% / 普通32% / 不調25% / 絶不調15%
* 特殊能力の有無による勝率差は **+2.5ポイント**（`scripts/ab-special.ts` で A/B 計測）

> ※ この高齢化の問題は PHASE 3.1 のドラフト・引退システムで解消済みです（下記参照）。

## PHASE 3.1：引退・ドラフト・世代交代

選手が成長し、ベテランになり、衰え、引退し、新人が入ってきて次世代の主力になる——
という循環を完成させました。

```
シーズン終了 → 年齢+1・成長／衰退 → 引退判定 → ドラフト候補生成 → ドラフト会議
→ 新人加入（2軍スタート） → ロスター再構築 → 翌シーズン開幕
```

年齢の加算は成長処理の中の1回だけで、引退・ドラフトでは加算しません。
同じシーズンで2回ドラフトが起きないよう `lastDraftYear` で冪等性を担保しています。

### 引退（`domain/retirement.ts`）

年齢を最重要要素とした確率判定です。25歳以下は0%、33歳で3%、35歳で12%、
38歳で50%、41歳以上で95%を基準に、次の補正がかかります。

* **能力**：総合が高いほど残りやすい（±35%まで）。ただし高能力でも40代の引退率は高い
* **出場機会**：出番のないベテランは最大+35%
* **怪我**：長期離脱中は+25%（怪我だけで即引退にはならない）

引退した選手はロスター・オーダー・ローテーションから外れ、
名前・球団・年齢・通算年数・最終総合が `retiredPlayers` に記録されます（将来の殿堂用）。

### ドラフト（`domain/draft.ts`）

* **候補**：毎年 12球団 × 9人 = **108人**。年ごとに「当たり年・不作年」の差が少しつきます
* **新人**：18〜22歳（高卒18歳が中心）。既存の `createPlayer()` をそのまま使うので、
  性格・成長タイプ・潜在能力・特殊能力・調子・モチベーションはすべて通常の選手と同じ仕組みです
* **指名順**：前年成績の悪い球団から。同率はシード乱数で決定
* **巡数**：各球団の不足人数（目標25人）から決まり、最大6巡。埋まった球団はパス
* **CPU評価**：`現在能力×0.50 + 潜在能力×0.30 + ポジション不足×0.15 + 適性×0.05`（+わずかな揺らぎ）

**潜在能力の実数値はUIに表示しません。** 候補カードには「将来性：非常に高い〜非常に低い」の
ラベルだけを出し、`projectedPotential` として保持しています。
PHASE 3.2 でスカウト精度（`scoutedPotentialLabel`）を差し込めるよう、
「内部の真の潜在能力」と「プレイヤーに見える情報」を分離してあります。

### 世代交代の検証（143試合 × 20シーズン）

| | 開始 | 5年目 | 10年目 | 15年目 | 20年目 |
| --- | --- | --- | --- | --- | --- |
| 平均年齢 | 26.3 | 28.0 | 28.1 | 27.4 | 27.7 |
| 平均総合 | 37.5 | 41.0 | 41.4 | 40.9 | 39.9 |
| 22歳以下 | 84人 | 34人 | 63人 | 65人 | 48人 |
| ロスター | 25人 | 25人 | 25人 | 25人 | 25人 |

* **平均引退年齢 36.5歳 / 年間 約17人が引退し、同数の新人が加入**
* 平均年齢は26〜28歳で安定（PHASE 2.5 では10年で36歳まで高齢化していました）
* リーグ平均総合は40前後で頭打ちになり、青天井のインフレは起きません
* 最高総合も65〜71で、初期（67）と同水準

## PHASE 3.2：スカウト

ドラフトを「一覧から強い選手を選ぶだけ」ではなく、
**限られた情報から将来活躍する選手を見抜く**意思決定にしました。

### 真のデータと、見えている情報を分ける

```
Player（真のデータ）          ScoutReport（球団が調査で得た推定）
├ 基本能力                    ├ 推定現在能力（幅のある評価）
├ 潜在能力                    ├ 推定将来性（5段階ラベル）
├ 性格                        ├ 推定性格（「努力家？」など）
├ 成長タイプ                  ├ 推定成長タイプ（「晩成傾向」など）
└ 特殊能力                    ├ 発見済みの素質・弱点
                              └ 項目ごとの調査進行度と信頼度
```

ScoutReport は **Player の真の値を一切書き換えません**。
UIに出るのはすべて ScoutReport の推定情報で、潜在能力の実数値は表示されません。

### スカウト能力（球団ごと）

| 項目 | 影響 |
| --- | --- |
| 能力の見極め | 現在能力の推定誤差と評価幅 |
| 将来性の見極め | 将来性ラベルの正確さ（既存の `scoutedPotentialLabel()` を使用） |
| 人物調査 | 性格・成長タイプの正確さ |
| 素質の発見 | 特殊能力の発見率と、名前・Lvが分かるまでの深さ |

情報精度は `0.18 + (0.25 + 能力/100 × 0.45) × 調査進行度 × 1.18`（上限0.97）で、
**スカウト能力と調査進行度の両方**で決まります。
能力が低い球団は100%調査しても完全には見抜けません。

### 調査ポイント（年60ポイント）

| 調査 | コスト | 1回の進行 |
| --- | --- | --- |
| 現在能力 | 2pt | +34% |
| 将来性 | 4pt | +34% |
| 性格・成長タイプ | 3pt | +34% |
| 特殊能力 | 4pt | +34% |

* 1人を全項目100%まで：39pt → **1.5人**
* 現在能力＋将来性を1段階ずつ：6pt → **10人**
* 現在能力だけ1段階：2pt → **30人**

「誰を重点的に調べるか」を選ぶ設計です。候補108人を全員調べることはできません。

### 情報精度の実測（候補120人・`scripts/scouting-balance.ts`）

| スカウト | 進行度 | 現在能力の平均誤差 | 評価幅 | 将来性の正解率 | 信頼度 |

## PHASE 3.3：契約・年俸・球団経営

金額の単位は **1 = 100万円** です（表示は自動で「◯◯万円 / ◯.◯◯億円」に変換されます）。

### 契約（`domain/contract.ts`）

すべての選手が `Contract` を持ちます。

| 項目 | 内容 |
| --- | --- |
| `salary` | 年俸（15〜1500 = 1500万円〜15億円） |
| `years` / `yearsRemaining` | 契約年数と残り年数 |
| `signedYear` | 契約した年 |

契約可能な年数は年齢で決まります（27歳以下 5年 / 32歳以下 4年 / 35歳以下 3年 / 36歳以上 2年）。
シーズンが明けるたびに残り年数が **1年だけ** 減り、0になった選手が契約更改の対象になります。

### 年俸の決まり方

```
市場価値 = 26 × exp((総合 - 32) / 17)
         × 年齢係数 × (1 + 成績係数) × 経験係数
```

* **年齢係数** … 21歳以下 0.55 → 28〜32歳 1.00 → 36歳以上 0.80（ピークは20代後半〜30代前半）
* **成績係数** … 打者は打率・本塁打・打点、投手は防御率・勝利・セーブから算出
* **経験係数** … デビューからの年数（若手は抑えめ）

選手の希望額は `max(市場価値 × 0.92, 現年俸 × 0.55)`。
**大幅な減俸は受け入れません**が、複数年契約なら年あたり2%ずつ譲歩します（最大8%）。
提示が希望額を下回ると交渉決裂で、その選手は退団します。

### 球団の財務（`TeamFinance`）

| 項目 | 内容 |
| --- | --- |
| `cash` | 球団資金（16億円前後で開始） |
| `budget` | 年間予算（14億円前後） |
| `annualRevenue` | 年間収入 |
| `payroll` | 総年俸（選手の年俸合計、自動再計算） |
| `lastResult` | 前年度の収支 |

シーズン終了時に **1回だけ** `資金 += 年間収入 - 総年俸` を精算します
（`lastPayrollYear` で二重支払いを防止）。予算超過や資金マイナスは警告として表示されますが、
**破綻（ゲームオーバー）はしません**。

### 新人の契約

ドラフトで獲得した新人には `市場価値 × 0.7 + 巡目ボーナス` の年俸が自動で付きます
（1巡目 +14 / 4年、2〜3巡目 +7 / 3年、それ以降 2年）。
新人が既存の若手を上回る年俸にならないよう調整しています。

### 契約更改の流れ

```
シーズン終了 → 引退 → ドラフト（スカウト → 指名）→ 契約更改 → 新シーズン
```

契約更改画面では、契約満了の選手ごとに年俸と年数を提示します。
提示中は「◎ 受け入れられそうです / × この条件では拒否されそうです」が表示され、
予算残りもリアルタイムで確認できます。「おまかせで交渉する」で残り全員を自動処理できます。

CPU球団は最低24人を維持しながら、予算の1.12倍を上限に主力から順に更改します。
予算に収まらない選手は契約せず、そのまま退団します。

## PHASE 3.4：FA（フリーエージェント）市場

契約更改で残らなかった選手が市場に出て、12球団が予算・戦力・ポジション事情を
にらみながら奪い合います。オフシーズンの流れは次のとおりです。

```
シーズン終了 → 年俸支払い → 成長・衰退 → 引退 → ドラフト
  → 契約年数 -1 → 契約更改 → FA市場 → 一斉解決 → ロスター再構築 → 翌シーズン
```

### FA選手の持ち方（`domain/freeAgency.ts`）

未所属の選手は `state.players` から外し、**`state.freeAgents`** で保持します。
所属していない選手が試合に出たり成績が付いたりする事故を、構造として起こらなくするためです。

* 契約更改が成立しなかった選手 → 球団を離れて FA 市場へ（**選手データは消えません**）
* 引退した選手は FA 市場に入りません
* 同じ選手が二重に登録されることはありません（読み込み時にも修復します）
* 契約が決まらなかった選手は翌オフも市場に残ります（強制引退はしません）

### 希望条件

| 項目 | 決まり方 |
| --- | --- |
| 希望年俸 | `max(市場価値, 直近年俸 × 0.7) × 売れ残り係数` に ±5〜12% の揺らぎ |
| 最低ライン | 市場価値の 70%。これを下回る提示は原則成立しません |
| 希望年数 | 若手ほど長期（25歳以下4年 → 34歳以上1年）。年齢別の上限は超えません |
| 市場評価 | S / A / B / C / D のラベル（内部の数値は見せません） |

決まらないまま年を越した選手は、要求を年 18%（最大 60% まで）下げて再挑戦します。

### 選手の選び方（Offer Score）

年俸だけでは決まりません。

```
評価 = 年俸 0.55 + 契約年数 0.10 + 球団の強さ 0.10
     + 出場機会 0.10 + ロスターの余裕 0.10 + 乱数 0.05
```

* **年俸** … 希望額の 60% で 0、120% で 1
* **球団の強さ** … 前年の勝率
* **出場機会** … 同じポジションに自分より上の選手が何人いるか
* **ロスターの余裕** … 保有人数が少ない球団ほど出番がある

「強い球団に行きたいが出番がない」というトレードオフが生まれ、
高額提示が必ず勝つわけではありません。

### CPUの補強

CPU は**真の潜在能力を参照しません**。見えている能力にスカウト精度ぶんの誤差を乗せた
推定値と、成績・年齢・ポジション・市場価値・チーム事情で判断します。

優先順位は **ロスター不足 > ポジション不足 > 主力補強 > 若手 > 余剰** の順。
1球団あたり主力候補に最大3人、控えの確保に最大2人までオファーします。
総年俸は PHASE 3.3 と同じ **予算 × 1.12** を超えられません。

* 同時に提示できるのは **8人まで**
* 年俸（±ボタン）と契約年数（年齢別の上限まで）を指定して提示

## PHASE 3.5：トレード

シーズン中に球団同士が選手を交換します。単なる「強い選手の奪い合い」ではなく、
**今の勝利を取るか、将来を取るか**を選ぶ仕組みにしています。

```
シーズン開幕 → トレード期間 → トレード期限 → シーズン終了 → オフシーズン
```

### トレード期間（`domain/trade.ts`）

* シーズン日程の **75% を過ぎた日**がトレード期限
* オフシーズン（ドラフト・契約更改・FA）中はトレード不可
* CPUからの提案は **5日**で期限切れ

### トレードできる選手

契約中の選手だけが対象です。

| 状態 | トレード |
| --- | --- |
| 契約中 | できる |
| 契約満了・無契約 | できない |
| FA（未所属） | できない（FA市場でのみ獲得） |
| 引退 | できない |
| 故障中 | **できる**（ただし評価は下がる） |
| 今季すでにトレードされた | できない |

### トレード価値

```
価値 = 資産価値 − 契約の負担

資産価値 = 市場価値（能力・年齢・成績・実績）
         × 年齢による長期係数
         × 伸びしろ係数（推定潜在能力）
         × 故障係数
         × 特殊能力係数（±10%まで）

契約の負担 = 年俸 × 残り年数 × 0.18
```

* **その日の調子・疲労は使いません**（一時的な状態で価値が乱高下しないように）
* 特殊能力1つで価値が跳ね上がらないよう、影響は全体で ±10% までに制限
* 高額・長期契約はそのぶん負担として差し引かれます

この式により、たとえば **35歳・総合68・年俸2.2億（残り1年）** と
**24歳・総合55・年俸5000万（残り3年）** の価値が近くなります。
現在戦力では前者が上でも、長期価値では後者が追いつきます。

### 受け入れの判断

```
比率 = 受け取る価値 ÷ 渡す価値
```

受け取る側は、ポジションの需要・補強方針・自分の層の厚みで補正した価値を比べ、
**比率が 1.05〜1.13 以上（球団ごとに少し違う）** なら受け入れます。
これにより、弱い選手を出して強い選手を要求する取引は通りません。

断られた理由は「戦力面で釣り合わないと判断しました」のように**抽象的な文章**で返し、
内部の数値は表示しません。

### 球団の補強方針

seed から決まる軽い性格づけを持たせています。

| 方針 | 傾向 |
| --- | --- |
| 今季優先（WIN_NOW） | 27〜34歳を高く評価、若手は低め |
| 若手育成（YOUTH） | 25歳以下を高く評価、33歳以上は低め |
| 堅実経営（BUDGET） | 高額年俸を避け、安い選手を好む |
| バランス（BALANCED） | 標準 |

### CPUのトレード

* CPU同士もトレードし、ユーザーが介入しなくてもリーグが動きます
* CPUは**真の潜在能力をそのまま参照しません**（自球団の選手は把握、他球団はスカウト精度ぶんの誤差）
* 優先順位は「手薄な枠を埋める」→「余っている枠から出す」
* 提案する側は釣り合えば動き、受ける側はより厳しく判断します
* プレイヤーへの提案は同時 **2件**まで（通知だらけにならないように）
* 1球団の成立は1シーズン **4件**まで、同じ選手は1シーズン **1回**まで

### 守っている制約

* トレード後も両球団が **25人以上**（リーグ最低の24人＋1人の余裕）
* トレード後も野手11人・投手8人以上（怪我が重なっても1軍の野手9人・投手5人を組めること）
* トレード後の総年俸が **年間予算 × 1.12** を超えない
* 契約（年俸・残り年数・契約年）はそのまま選手と一緒に移動する
* 検証を通してから一括で反映するため、**片方だけ移動する状態は起きません**

### 記録

* **トレード履歴**（`trade.history`）はシーズンをまたいで残ります
* **在籍履歴**（`player.ext.careerTeams`）に入団・トレード・FA移籍が記録されます
* 成績は選手についていくため、移籍時点の成績を記録に残し、球団別の集計を復元できます

* 優勝の偏りも最大 **10.9%**（均等値 8.3%）で、1球団の独走は起きていません
* 年俸のインフレなし・平均総合 37.8〜41.6・平均年齢 26.3〜28.3 と、PHASE 3.4 の傾向を維持
* 全球団が常に 24 人以上、1軍は野手9人・投手5人を維持

### PHASE 3.5 で実装していない機能

ドラフト指名権のトレード / 金銭トレード / カウンターオファー / 外国人獲得 /
スポンサー・チケット・グッズ収入 / 経営破綻

**これらはUIにも配置していません。**

## PHASE 3.6：球団経営AI

契約・ドラフト・FA・トレードを個別に判断していた CPU を、
**ひとつの経営プラン**でつないだフェーズです。

```
シーズン終了 → 戦力分析 → 球団戦略 → 補強ポイント → 予算配分
  → 契約更改 → ドラフト → 補強ポイント再計算 → FA → トレード → 翌シーズン
```

### 戦力分析（`domain/rosterAnalysis.ts`）

ポジションを 8 つの枠（捕手 / 一塁 / 二塁 / 三塁 / 遊撃 / 外野 / 先発 / 救援）に分け、
それぞれの**補強必要度を 0〜100** で出します。人数だけでは判断しません。

| 状態 | 必要度 |
| --- | --- |
| 選手がいない | 100 |
| 全員が総合30台 | 75 前後 |
| 主力48・控え29 | 60 前後 |
| 主力55・控え45 | 35 前後 |
| 主力65・控え55 | 15 前後 |

「遊撃が3人いても全員が総合30」は「2人でも55と50」より不足度が高くなります。
選手は STARTER / BACKUP / DEPTH / PROSPECT に分類され、投手はスタミナで先発と救援に分かれます。

### CPUが見てよい情報

分析に渡すのは **`KnownPlayer`** という型だけで、真の潜在能力は入っていません。

* 自球団の選手 … 潜在能力まで把握している（プレイヤーも自分の選手は見られる）
* 他球団の選手 … スカウト精度ぶんの誤差が乗った**推定値**
* ドラフト候補 … PHASE 3.2 のスカウト情報のみ（未調査なら公開情報だけ）

型として隠し情報を渡せないので、CPU が有利になる抜け道が生まれません。

### 球団戦略（`domain/teamStrategy.ts`）

毎年、戦力・年齢構成・財務・前年成績からスコアを出して決めます。固定の性格ではありません。

| 戦略 | 選ばれやすい状況 |
| --- | --- |
| 優勝を狙う（WIN_NOW） | リーグ平均より強い・前年好成績・年俸に余裕 |
| 若手を育てる（YOUTH） | 戦力が低い・ベテラン比率が高い・前年不振 |
| 支出を抑える（BUDGET） | 総年俸が予算を圧迫・資金が少ない |
| 戦力を維持する（BALANCED） | 上記の中間 |

戦力は**リーグ平均との比較**で見ます（絶対値で見ると、リーグ全体の能力が上がった年に
全球団が WIN_NOW になってしまうため）。決定には ±3〜8% の揺らぎを入れ、完全最適化はしません。

球団ごとに seed から決まる**経営の癖**（積極性 / 若手志向 / 支出規律 / トレード活発さ /
FA積極度 / ベテラン志向）があり、同じ状況でも判断が少し変わります。

### 経営プラン（`domain/teamAi.ts`）

戦略が決まると、その年のプランが作られます。

* **補強ポイント** … 枠ごとの必要度（戦略で重みづけ）
* **FA予算** … 年間予算に対する割合（WIN_NOW 35〜50% / BALANCED 20〜35% / YOUTH 10〜25% / BUDGET 0〜15%）
* **実行ログ** … 残留・放出・指名・FA獲得・トレードの件数

### 施策どうしの連携

PHASE 3.6 の要です。

* ドラフトで遊撃を獲れた → FA・トレードでの遊撃の必要度が下がる
* FAで先発投手を獲れた → トレードで先発を追う優先度が下がる
* 補強ポイントが高い枠の選手は、トレードで**出さない**
* 配分した FA 予算を超える買い物はしない（人数が足りていない場合を除く）

### 年間予算がリーグ水準に追随する

PHASE 3.3 では年間予算がゲーム開始時の値で固定でした。リーグ全体の能力が上がると
年俸水準も上がるため、契約が残っているだけで総年俸が予算を大きく超え続ける球団が出ていました。

PHASE 3.6 では、年間予算を**リーグの選手価値の水準**（球団が実際に払っている額ではなく、
能力・年齢・実績から決まる市場価値）に緩やかに追随させます。
支払い額を参照すると「予算が増える→年俸が上がる→予算が増える」と際限なく膨らむため、
支払い額からは独立させています。

さらに、球団ごとの規模の差も**その球団が抱えている戦力の価値**に追随させます
（リーグ平均の 0.85〜1.3 倍の範囲）。厚い戦力を持つ球団は収入も大きい、という扱いです。
全球団を同じ予算に均すと、もともと年俸の高い球団は抱えている契約だけで
予算超過が続いてしまうためです。

### 予算に見合わない年俸の是正

ロスターが最低人数（24人）ちょうどだと、契約更改で誰も手放せず、
高年俸の選手を抱えたまま総年俸が膨らみ続けてしまいます。そこで:

* **割高な選手の入れ替え**に限り、一時的に最低人数を割ってよいことにしています。
  外れた選手は「年俸のわりに働ける順」で拾い直されるので、
  高年俸の選手を手放して安い選手で埋め直す動きになります。
* 見送りの候補は**優先度の下半分**に限定します（主力まで費用対効果で切らない）。
* 単純な予算切れによる打ち切りは、これまで通り最低人数で止めます。
* 拾い直しは**野手・投手の最低人数を満たす順**に行い、1軍が組めない構成にはしません。
  このときの年俸は、球団が払える範囲（予算の30%）に収めます。

### UI

ホーム画面と、トレード画面の相手球団情報に表示します。

```
今季の方針      優勝を狙う
                前年の成績が良く、優勝を狙える位置にいます
補強ポイント    先発投手・遊撃手
FA積極度 / トレード積極度   高 / 中
```

内部のスコアや必要度の数値は表示しません（抽象的なラベルと説明文だけ）。

## PHASE 3.7：歴史・記録

10年、20年、30年と続けたときに「この選手は昔この球団にいた」「この年は優勝した」
「この選手が球団史上最高だった」を追える記録の層です。
ゲームの処理そのものには手を入れず、**結果を記録するだけ**の層として足しています。

```
既存のゲーム処理 → 試合結果 → 成績 → シーズン終了 → 歴史に確定
```

### 球団別の成績（トレード・FAとの分離）

試合結果には「出場したときに在籍していた球団」が入っているので、
そこから **選手 × 球団** の単位で成績を積みます（`state.teamStats`）。

シーズン途中にトレードされても、前の球団の成績が移籍先に混ざりません。
あとから復元する処理が要らないので、混入そのものが起きない作りです。

```
2028年  A選手
  東都   45試合 .285
  大阪   72試合 .310
  （合計 117試合 .300）
```

### シーズンの確定

シーズンが終わると、成長・引退でデータが変わる**前**に、その年を歴史へ確定します。

1. 選手のシーズン成績を球団別に記録
2. 球団の順位・勝敗・チーム成績を記録
3. タイトル・MVP・最優秀投手・新人王を決める
4. リーグ記録・球団記録を更新し、更新されたら出来事として残す
5. （引退時）歴史を確定して殿堂入りを判定

年で重複チェックしているので、**同じ年を二度確定しても成績が二重になりません**。

### 引退した選手

ロスターからは消えますが、歴史は残ります。
年度別成績・通算成績・所属球団・表彰・記録はそのまま保持され、以後変化しません。

### 殿堂入り

「能力が高かった」ではなく「何を積み上げたか」で決めます。
通算成績・ピーク・在籍年数・優勝・表彰・記録を見て、8年以上プレーした引退選手だけが対象です。
数字はシーズンの試合数に比例するので、143試合換算に直してから測ります。
50年プレイでおよそ35〜40人です。

### 保存量

年度別成績は決まった順番の数値配列で持ち、使い終わった `statsAtTrade` は
シーズンが変わったら空にしています。

| プレイ年数 | セーブサイズ | 読込（復元+migrate） |
| --- | --- | --- |
| 30年 | 約2.1MB | 約13ms |
| 50年 | 約3.1MB | 約21ms |

### UI

* ホーム → 「歴史」「記録」
* 歴史画面：年表 / 球団の歩み / 殿堂
* 記録画面：リーグ / 球団 / シーズン / 通算
* 選手詳細に年度別成績・通算成績・所属球団の歩み

引退した選手の画面では**能力値を出さず、当時の成績だけ**を見せます。

## PHASE 3.8：ポストシーズン・日本シリーズ

レギュラーシーズン1位がそのまま優勝だったものを、**勝ち抜いて日本一になる**形にしました。

```
レギュラーシーズン → 順位確定
  → ファーストステージ（2位 vs 3位・3戦2勝）
  → ファイナルステージ（1位 vs 勝者・1位に1勝のアドバンテージ・4勝先取）
  → リーグ優勝
  → 日本シリーズ（4勝先取）
  → 日本一
  → 歴史・記録へ
```

各リーグ上位3球団、あわせて6球団が進出します。

### シリーズ

| | 勝ち抜け | 最大試合 | ホーム開催 |
| --- | --- | --- | --- |
| ファーストステージ | 2勝 | 3 | 2位が2試合・3位が1試合 |
| ファイナルステージ | 4勝（1位は1勝からスタート） | 6 | 1位が4試合・挑戦側が2試合 |
| 日本シリーズ | 4勝 | 7 | 2-3-2 |

引き分けはどちらの勝利にもならないので、規定試合数で決着しないことがあります。
そのぶんは最大3試合まで足して、**必ず勝者が決まる**ようにしています。

### 既存システムとの関係

* 試合は**既存の試合エンジンをそのまま使います**。ポストシーズン専用の能力補正は入れません。
  調子・疲労・モチベーションは通常どおり働きます。
* レギュラーシーズンの順位・勝敗・個人成績には**一切加算しません**。
  ポストシーズンの成績は別に持ちます。
* 乱数は段階ごとの専用系列（`postseasonFirstStage` / `postseasonFinalStage` / `japanSeries`）です。
  共有の乱数状態を触らないので、**同じシードならレギュラーシーズンもオフシーズンも従来と同じ結果**になります。
* ポストシーズン中は引退・契約更改・FA・トレード・ドラフトが一切起きません。
  すべて従来どおりオフシーズンの処理で行います。

### 優勝の呼び分け

PHASE 3.7 までの「優勝」＝レギュラーシーズン1位は、意味を変えずに残しています。

| 呼び方 | 意味 |
| --- | --- |
| 1位（ペナント） | レギュラーシーズンの1位 |
| リーグ優勝 | ファイナルステージの勝者 |
| 日本一 | 日本シリーズの勝者 |

### MVP

* クライマックスシリーズMVP … リーグ優勝球団から、CSの成績で選ぶ
* 日本シリーズMVP … 日本一の球団から、日本シリーズの成績で選ぶ
* 年間MVPは従来どおり**レギュラーシーズンの成績**で決めます（混同しません）

### バランス（30シーズン × 100シード）

| 順位 | ファイナル進出 | リーグ優勝 | 日本一 |
| --- | --- | --- | --- |
| 1位 | 100% | 70.2% | 36.0% |
| 2位 | 53.3% | 16.6% | 8.4% |
| 3位 | 46.7% | 13.2% | 5.6% |

1位以外がリーグ優勝する「アップセット」は29.9%。
上位ほど有利ですが絶対ではなく、3000シーズンで12球団すべてが日本一を経験しています。

### UI

* ホームのシーズン終了カードに、進出状況と日本一を表示
* ポストシーズン画面：進出球団・シリーズの勝敗・各試合のスコア・1試合ずつ進める
* 歴史の年表に日本一とMVP、球団の歩みに「1位／リーグ優勝／日本一／CS進出／日本シリーズ出場」の回数

途中で保存して終了しても、**次に開いたときはその試合から再開**できます。

## PHASE 3.9：ニュース・シーズンストーリー

起きた出来事を**ニュース**として伝え、その年を1本の**物語**にまとめます。

```
試合・記録・移籍・引退・ポストシーズン
  → ニュース
  → 年度の物語
  → 歴史
```

### 最重要：ニュースは演出でしかない

ニュースは「起きたことの二次表現」で、**独自の事実を持ちません**。

* 能力・契約・順位・勝敗・乱数のどれにも触れません
* 乱数を使わないので、同じ状態からは必ず同じニュースができます
* IDは「年:カテゴリ:出来事」で決まるため、同じ出来事から二度作られません
* 出来事が起きたその場で1回だけ作ります（毎日すべての歴史を走査しません）

PHASE 3.8 と同じシードで長期検証を回すと、**ゲームの結果は完全に一致**し、
差はセーブサイズだけでした。

### 何がニュースになるか

すべての試合はニュースにしません。実際に取れた成績から、次のときだけ作ります。

| 種類 | 条件 |
| --- | --- |
| 選手 | 1試合3本塁打／4安打／5打点／完封／10奪三振／無安打無得点 |
| 試合 | 5点差以上の逆転／サヨナラ／10点差の大勝／延長 |
| 球団 | 5連勝・5連敗ごとの節目 |
| 記録 | リーグ記録の更新（球団記録は毎年たくさん入れ替わるので出しません） |
| 表彰 | MVP・最優秀投手・新人王・CS MVP・日本シリーズMVP |
| 移籍 | トレード成立・FA移籍/残留・大型契約・ドラフト指名 |
| 引退 | 引退（通算成績を添える。理由は作りません） |
| 怪我 | 14日以上の離脱だけ |
| ポストシーズン | 各シリーズの決着・日本シリーズの王手・惜敗 |

ドラフトのニュースは**その球団のスカウト評価**で表現し、真の潜在能力は使いません。

### 年度の物語

各年の終わりに、その年を象徴する1文と要点を残します。

```
2028年  3位からの下剋上、名古屋が日本一
2029年  喜多村 諒がリーグ通算安打記録を更新、博多が日本一
2030年  博多が圧倒的なシーズンを送り日本一
```

見出しは決まった規則だけで作ります（外部AIも乱数も使いません）。
下剋上・記録更新・大量の引退・ペナントからの完全制覇などを見て、
いちばん重い出来事を選びます。

### 保存量

ニュース本体は直近800件のローリング保存で、古いものから消えます。
**年度の物語は全年度残す**ので、50年プレイしても「その年に何があったか」は追えます。

| --- | --- | --- |
| 30年 | 約2.7MB | 約241KB |

## PHASE 4.0：球団経営・チームビルディング

「選手を集めて戦う」だけでなく、**球団を運営している手ごたえ**を足したフェーズです。
既存のシステム（成長・FA・トレード・ドラフト・ポストシーズン）は作り直していません。
すべて「上に乗せる」形で入っています。

```
球団方針 ─┬─ 施設への投資配分
          ├─ 経営目標の内容
          ├─ CPU の補強戦略（PHASE 3.6）
          └─ 起用方針の自動割り当て

施設 ─┬─ 育成：成長にかかる係数
      ├─ 医療：怪我の重さ・回復
      ├─ スカウト：調査ポイント
      └─ トレーニング：疲労の回復
```

### 最重要：基本能力には触れない

PHASE 4.0 のどの仕組みも、`player.batting` / `player.pitching` の値を**直接は書き換えません**。

* 施設は「成長のしやすさ」「怪我の重さ」「回復の速さ」に係数として効くだけ
* 起用方針は**出場機会だけ**を動かし、成長の上乗せはしない
* 育成環境は PHASE 2 の成長計算に上限つきの倍率として乗るだけ（最大 1.4 倍）
* 経営目標の達成も、球団の色（アイデンティティ）も、能力は動かさない

これを守れているかは専用のテスト（`phase40.test.ts` の「基本能力が変わらない」）で
全選手の能力値の指紋を取り、施設・方針・士気・イベント・育成・起用を通しても
一致することを確認しています。潜在能力の上限も越えません。

### 球団方針（5種類）

| 方針 | 効果 |
| --- | --- |
| 優勝狙い | 補強重視。施設への配分は少なめ |
| 若手育成 | 育成施設を優先。若手の出場機会が増える |
| 再建 | 施設への配分が最大。ベテランより若手 |
| バランス | 平均的 |
| 堅実経営 | 支出をおさえる。施設への配分は最小 |

自球団だけでなく**CPU球団も方針を持ち**、PHASE 3.6 の補強戦略に接続されています
（CPU AI 自体は作り替えていません。方針から戦略を選ぶ層を足しただけです）。

### 選手起用方針（5種類）

主力 / 準主力 / 育成 / 控え / ベテラン枠。**出場機会の優先度だけ**が変わります。
指定しない選手は年齢と実力から自動で割り当てられ、怪我をしている選手は自動的に外れます。

### 球団施設（4種類・Lv1〜5）

| 施設 | Lv5 での効き方 |
| --- | --- |
| 育成施設 | 成長の倍率 +24% |
| 医療施設 | 怪我の重さ −8% / 回復期間 −20% |
| スカウト施設 | 調査ポイント +24 |
| トレーニング施設 | 疲労の回復 +30% |

**有利になるだけ**です。怪我をゼロにもしませんし、スカウトの結果が確実にもなりません。
強化は球団資金から支払います（Lv2:400 / Lv3:700 / Lv4:1100 / Lv5:1600）。
経営破綻はありません。CPU球団も方針に応じた配分で投資し、
配分にはシードから決まる ±10% のばらつきが入ります（毎回同じ結果になります）。

### 経営目標と球団評価

シーズンの初めに方針に応じた目標が立ち、シーズンの終わりに判定されます。
判定は年ごとに1回だけで、二度呼んでも達成数は増えません。

球団評価は **戦力 / 将来性 / 財務 / 育成 / 経営** の5つと総合（0〜100）です。
これは「見え方」であって、**勝率を言い当てるものではありません**
（30シーズン×100シードでの相関は 0.1 前後）。

### 経営判断イベント

若手の台頭・主力の不振・連敗・トレード期限などで、ときどき判断を求められます。
毎日は起きませんし、まとめて生成もしません。発生も結果もシードから決まります。

### PHASE 4.0 で実装していない機能

外国人選手 / スポンサー・チケット・グッズ収入 / 経営破綻 /
ドラフト指名権のトレード / 金銭トレード / カウンターオファー /
複雑な契約交渉ミニゲーム

**これらはUIにも配置していません。**

## PHASE 4.1：分析と演出

数字を増やすフェーズではありません。**すでにある数字を、判断できる形にして見せる**フェーズです。

```
選手詳細 ─┬─ レーダーチャート（現在の推定能力）
          ├─ 年度別成績のグラフ（↑ 成長 / → 安定 / ↓ 下降）
          ├─ 球団分析（一言）
          ├─ 起用分析（1軍 / 2軍 / 育成 / 競争 / 休養）
          └─ 扱いの目安（中心 / 維持 / 育成 / 調整 / 整理）

球団画面 ─┬─ チーム戦力分析（7軸・リーグ平均との差）
          ├─ 現在の課題（最大3件）
          └─ ポジション別の層（1軍主力 / 候補 / 2軍 / 育成）
```

### 最重要：分析は読むだけ。ゲームには触らない

`domain/playerAnalysis.ts` と `domain/teamAnalysis.ts` は**状態を書き換えません**。

* 乱数を引かないので、何度分析してもゲームの結果は 1 ミリも変わりません
* 現在時刻も使わないので、同じデータからは必ず同じ分析・同じ文章になります
* 文章はテンプレートを組み立てているだけで、LLM も外部APIも使いません
* 助言は助言でしかなく、1軍/2軍の登録を勝手に変えることはありません

同じシードで 30シーズン × 100シード を回すと、**PHASE 4.0 と結果は完全に一致**します。

### 潜在能力の実数値は出しません

分析が使うのは PHASE 2 から表示している**5段階の粗いラベル**だけで、
`Player.ext.potential` の数値そのものはどこにも出しません（テストで確認しています）。

* 潜在能力が 1 違っても、星の数は変わりません
* 将来予測のレンジは「確定値ではない薄い領域」として描きます
* 他球団の選手は情報の確度が低く、予測レンジも広くなります
* 29歳以上や伸びしろの小さい選手には、そもそも予測レンジを出しません

### 5段階の評価

S（主力・中心選手）/ A（1軍戦力）/ B（育成・競争枠）/ C（2軍調整候補）/ D（整理・放出検討）。

能力だけでは決めません。直近成績・年齢・成長傾向・出場状況・怪我・起用方針・
球団方針・契約・情報の確度をまとめて見ます。

そして **D＝即クビではありません**。「整理候補」は
「低能力・低成績・伸びしろ小・高齢・出場少・年俸高」が**4つ以上重なったとき**にだけ出て、
必ず重なった理由を並べます。若い選手は同じ条件でも整理候補にはならず、育成候補になります。

### アニメーション

「情報が現れる」「結果が確定する」「数字が変わる」を伝えるためだけに使います。

| 場面 | 演出 |
| --- | --- |
| 画面遷移 | 不透明度だけ 150ms（位置は動かさない＝押し間違いを防ぐ） |
| ホーム | 初回だけカードが上から順に出る。戻ってきたときは即表示 |
| レーダーチャート | 外周 → 軸 → 能力の順に約700ms。2回目以降は260ms |
| 試合結果 | 回ごとにスコアが進む。スキップ可 |
| ドラフト | 球団 → 指名順 → 選手 → 評価 → 指名決定。スキップ可 |
| FA | 選手 → 年俸 → 年数 → 加入 |
| トレード | OUT が抜けて IN が入る |
| ポストシーズン | シリーズ決着で WIN、日本一だけ特別扱い |

**演出とゲームロジックは完全に分けています。**
試合は engine が一括で計算済みで、画面は決まった結果を順番に見せているだけです。
スキップしても、途中で画面を離れても、リロードしても結果は変わりません。
演出の途中経過はセーブに一切書きません。

### 視差効果を減らす設定（prefers-reduced-motion）

OS で「視差効果を減らす」が有効なときは、動きをほぼ止めます。
グラフは最初から完成形で表示され、**情報が減ることはありません**。

### PHASE 4.1 で実装していない機能

能力値の履歴（過去の能力推移）/ 選手同士の比較画面 / リーグ全体のランキング分析 /
Canvas・WebGL を使った演出 / 試合中のリアルタイム描画

**これらはUIにも配置していません。**
過去の能力履歴はセーブに持っていないため、**作り出さずに「記録していません」と表示**します。

### 試合シミュレーション

完全ランダムではなく、**打席ごと**に打者能力と投手能力・守備力から結果を決めます。

* 投手力：球速・制球・スタミナ・球威・変化量（スタミナが切れると能力が低下し、救援に交代）
* 打撃力：ミート・パワー（弾道は加算せず、独立した係数として長打・本塁打率に作用）
* 守備力：守備・捕球・肩（**本職と違う守備位置ではペナルティ**が入り、失策率も上がる）
* 四球 → 三振 → 本塁打 → 失策 → 安打（単打/二塁打/三塁打）→ 凡打（ゴロ/フライ/併殺/犠飛）の順で判定
* 盗塁は走者の走力と捕手の肩で成否が決まる
* 9回裏でホームがリードしていれば裏の攻撃なし。同点なら延長12回まで、決着しなければ引き分け

チーム能力が高いほど勝率は上がりますが 100% にはなりません（ゲーム内で起こりうる最大の戦力差でおよそ 6〜7 割）。

### 弾道について

弾道も他の基本能力と同じ **1〜100（G〜Aランク）** で扱います。
ただし弾道は他の能力とは意味が異なるため、**試合計算では他能力と同じ割合で加算しません**。
`domain/trajectory.ts` に独立した係数として切り出し、MatchEngine（`domain/simulation.ts`）は
この係数を通してのみ弾道を参照します。

| 係数 | 用途 | 弾道25 | 弾道50 | 弾道75 | 弾道100 |
| --- | --- | --- | --- | --- | --- |
| `homeRunFactor()` | 本塁打発生率に乗算 | 0.55 | 0.85 | 1.15 | 1.45 |
| `extraBaseFactor()` | 二塁打の出やすさに乗算 | 0.875 | 1.00 | 1.125 | 1.25 |
| `groundBallRate()` | 打球のゴロ率 | 0.65 | 0.56 | 0.47 | 0.38 |

旧仕様（1〜4の4段階）のセーブデータは読み込み時に **1→25 / 2→50 / 3→75 / 4→100** へ自動移行します
（`domain/save.ts` の `migrate()`、セーブスキーマ v1 → v2）。

## セーブデータの互換性

セーブデータは `version` を持ち、`domain/migrate.ts` が古いデータを変換します。

| version | 内容 | 移行処理 |
| --- | --- | --- |
| v1 | PHASE 1（弾道 1〜4） | 弾道を 1→25 / 2→50 / 3→75 / 4→100 に変換 |
| v2 | 弾道 1〜100 | PHASE 2 のデータ（性格・潜在能力・成長タイプ・特殊能力・状態）を安全な初期値で補完 |
| v3 | PHASE 2 | 調子の履歴などPHASE 2.5のフィールドを補完 |
| v4 | PHASE 2.5 | 引退記録・ドラフトのフィールドを補完 |
| v5 | PHASE 3.1 | スカウト能力・調査ポイントを補完 |
| v6 | PHASE 3.2 | 契約・球団財務（`finances` / `contract`）を市場価値から補完 |
| v7 | PHASE 3.3 | FA市場・未所属選手のフィールドを補完（既定は空） |
| v8 | PHASE 3.4 | トレード・在籍履歴のフィールドを補完（既定は空） |
| v9 | PHASE 3.5 | 球団経営AIのプランを補完（既定は空。次のオフシーズンで作られる） |
| v10 | PHASE 3.6 | － |
| v11 | PHASE 3.7 | 歴史は空から始める（過去は捏造しない） |
| v12 | PHASE 3.8 | 過去年度の順位・優勝は作り直さない |
| v13 | PHASE 3.9 | 過去のニュースはさかのぼって作らない |
| v14 | PHASE 4.0（現行） | 球団経営（方針・施設Lv1・目標・起用・イベント）を初期値で補完。CPUの方針は戦略から決める |

PHASE 4.1 は分析と演出だけを足したフェーズで、保存するデータを増やしていません。
セーブのバージョンは **v14 のまま**です（分析値はすべて既存データから毎回計算します）。

補完は選手IDから決まる乱数で行うため、同じセーブを読み直しても同じ結果になります。
既存の能力・成績・順位・日付・1軍/2軍・7日制限は一切書き換えません。
DH制は `League.useDH` で切り替わり、リーグごとに設定できます（オーシャンリーグがDH制）。
